# Convoy motion and mobile background behavior

Checked 19 October 2026 for Android and iPhone.

Member pins blend corrections over 600 ms and predict using reported speed and heading, or plausible consecutive fixes when these are missing. Estimates are marked `~` with a dashed pin border. Prediction is limited to three seconds and 90 metres; stationary, old, disconnected and implausibly jumping tracks do not glide indefinitely. The display estimate never replaces reported GPS or influences server regroup decisions. Animation pauses in hidden pages, stops when tracks settle, and is removed with its map layer.

## What this PR supports

- A persistent app-level convoy session across PhotoScout pages.
- Heartbeat recovery, fresh GPS acquisition and chat catch-up on return, including restoration from the browser's back/forward cache.
- Opt-in screen wake lock while visible; a denied or released wake lock is shown as unavailable.
- Installable PWA with a Convoy home-screen shortcut, plus install/background guidance in Riding & audio.
- Device alerts through an active service worker where available, with a desktop notification fallback. Tapping an alert opens the relevant convoy on the same origin.

The current notifications are generated by the running page. They **do not** provide server-originated Web Push delivery after the OS suspends or terminates that page. Lock-screen behavior, headset output and real GPS movement still need physical-device testing.

## Platform limits and next steps

| Requirement | Android browser / installed PWA | iPhone Home Screen web app |
| --- | --- | --- |
| GPS while PhotoScout is visible | Supported with permission | Supported with permission |
| Keep visible screen awake | Best effort; OS may refuse/release | Best effort; OS may refuse/release |
| Continuous GPS after switching apps or locking | Cannot be guaranteed through the web API | Cannot be guaranteed through the web API |
| Alerts after the page has been suspended | Requires a Web Push server and a push subscription | Requires a Web Push server and a push subscription; installation to Home Screen is required |
| Reliable ongoing ride tracking in background | Needs native location integration and the applicable foreground-service/permission handling | Needs native Core Location background integration and the applicable capabilities/authorization |

The [Geolocation specification](https://www.w3.org/TR/geolocation/#request-a-position) restricts position delivery to visible, fully active documents. Service workers do not expose `navigator.geolocation`, so moving the WebSocket or polling into a worker does not create background GPS. [Screen Wake Lock](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API) applies to visible documents and is not a CPU/background execution entitlement. [Periodic Background Sync](https://developer.chrome.com/docs/capabilities/periodic-background-sync) has browser-controlled timing and cannot serve as a real-time convoy connection.

True background **alerts** are feasible on both platforms through standards-based Web Push; [WebKit documents Home Screen push support](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/). A follow-up would need authenticated, revocable subscriptions bound to active convoy membership and session expiry, bounded push delivery, and physical iOS/Android verification. It should not send coordinates or chat history to a push service by default.

For true background **GPS**, the app needs native integration rather than only packaging the same web view. Relevant platform guidance: [Android background location](https://developer.android.com/develop/sensors-and-location/location/background) and [Apple background location](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background). Native packaging, signing, distribution and on-device testing are outside this web PR.
